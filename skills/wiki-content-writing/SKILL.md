# 写入 wiki 知识库（app/wiki/data.ts）

把外部长文（飞书文档导出、Markdown 稿）整理进本项目 `app/wiki/data.ts` 时，**Markdown 语法在飞书导出 + react-markdown 渲染这条链路上有大量隐性坑**。这次做了 9 期内容、修了 6 个 commit 才收敛，以下是必须遵守的规则。

## 数据结构

```
WIKI_META    : 一套 wiki = { slug, name, chapters[] }
               chapter  = 主题分类（如"数据分析"）
               entries  = 引用 entry id 列表
WIKI_ENTRIES : entry = { id, term, oneLiner, body[] }
               body[] 是按 `##` 切分后的段落数组，页面用 body.join("\n\n") 交给 react-markdown
```

**层级约定**（一期一篇长文）：

| Markdown | 含义 |
| --- | --- |
| `##` | 分组（如"二、指标体系"）—— **也是 body 的切分点** |
| `###` | 本篇内的大节 |
| `####` / `#####` | 更细层级 |

**`##` 是 body 切分点这件事很关键**，列表编号的重置规则必须与它对齐（见下文）。

## 处理链（顺序不能乱）

```
原文 md
 → clean()              剥模板 / 层级归一化 / 加多级编号   (process_issue.py)
 → merge_paragraphs()   合并连续正文段落
 → separate_list_items()规范化列表项间距
 → renumber()           规范化有序列表编号
 → 写入 data.ts
```

**顺序不能调换**，`renumber` 必须在最后（它依赖前面已经理顺的列表结构）。

## 必查项（每条都真实踩过）

### 1. 加粗：定界符紧邻标点会失效

CommonMark 规定 `**` 的右侧不能紧跟标点、左侧不能紧跟标点+非空白。飞书导出稿大量违反：

| 原文写法 | 渲染结果 | 修法 |
| --- | --- | --- |
| `**抽象对象：**顾名思义` | 不渲染 | `**抽象对象**：顾名思义` |
| `技术要求**：算法+数据**` | 不渲染 | `技术要求：**算法+数据**` |
| `**「价格导向」的客户**` | 不渲染 | `「**价格导向」的客户**` |
| `**"非关系型数据库"**` | 不渲染 | `"**非关系型数据库**"` |
| `**《书名**》` | 不渲染 | `《**书名**》` |
| `4**） 商品删除**` | 不渲染 | `4）**商品删除**` |

**必须用「按 `**` 两两配对 + 逐对规范化边界」实现**（`process_issue.py: _fix_line`）。
用正则一次性替换会**跨对误匹配** —— 例如 `**A**：**B。**` 会被搅成 `**A****：B。**`。

> 排查方法：`页面正文里数 textContent 中的 "**" 个数`，应为 0。

### 2. 标题：`#` 后的空格是语法的一部分

剥模板 / 清理空格时**不能动标题行**。曾因一条「删掉 `**` 前多余空格」的规则把
`## **项目回顾**` 变成 `##**项目回顾**`，**整篇标题全部不渲染**。

```python
is_heading = bool(re.match(r"^\s*#{1,6}\s", ln))
if is_heading:
    continue   # 跳过所有空格清理
```

### 3. 列表标记：`-` / `1.` 后必须有空格

原文大量写作 `-**MySQL入门**`、`1.**基本模型**`（标记与内容之间无空格），Markdown 不认。

补空格时必须排除三类误伤：
- `**加粗**`（两个星号连写，第二个才是定界符）
- `---` / `***` 分隔线
- `*斜体*`（行内存在成对星号）
- 小数 `2.5`（不是有序列表）

### 4. 列表编号：`1.` `1.` `1.` 不会自动递增

飞书里作者把「一串 `1.`」当项目符号（编辑器自动显示 1/2/3），**导出后全都真的是 `1.`**。

`renumber()` 规则：
- 在**同一个 `##` 范围内**连续累加（因为 body 按 `##` 切分，react-markdown 在每段内用 `start` 属性续号）
- 遇到下一个 `##` 才重置
- `1）` 与 `1. ` 视为同一序列（中文右括号在原文极常见）

> **为什么起始编号必须是真实数字**：react-markdown 会把被正文隔开的多个 `<ol>` 用 `start` 属性串起来，而 `start` 的值**直接取自数据里写的数字**。写 `1. 1. 1.` 就渲染成 4 个 `1.`；写 `1. 2. 3.` 才正确。

### 5. 空行：删了会粘连，多了会松散

- **`strip_template` 必须保留空行** —— 曾因 `if not s: continue` 把空行全删，导致「正文 + `1.列表项`」粘成一段，**列表根本不渲染**
- **列表项之间不要插空行** —— 会被拆成多个 `<ol>`，各自从 1 重新计数
- **列表项与正文之间要保留空行** —— 否则正文被吸进列表项

### 6. 列表标记：Tailwind preflight 会重置

`globals.css` 首行 `@import "tailwindcss"`，其 preflight 会把所有 `ul`/`ol` 的
`list-style` 重置为 `none`。必须在 `.wiki-markdown` 显式恢复：

```css
.wiki-markdown ul { list-style: disc outside; }
.wiki-markdown ol { list-style: decimal outside; }
.wiki-markdown ul ul { list-style: circle outside; }
.wiki-markdown ol ol { list-style: lower-alpha outside; }
```

### 7. 清理推广内容

飞书手册每期都带模板内容，按需删除：
- `<callout>` 署名块、`# ▌合集目录` 块
- 品牌图片（`![...](https://feishu.cn/file/...)`）
- 文末「扫二维码咨询…」
- `<cite doc-id="...">` 飞书引用
- 「本项目内容来自各平台」署名行

## 验收清单

改完必须逐项验证（用真实浏览器，不要只看源码）：

| 检查项 | 通过标准 |
| --- | --- |
| 残留 `**` | 正文 textContent 中 `**` 计数 = 0 |
| 未渲染 `#` | 正文中 `^#{1,6}[^ #]` 计数 = 0 |
| 裸 `-` | `<p>` 里以 `- ` 开头的计数 = 0 |
| 列表编号 | 相邻 `<ol>` 的 `start` 与项数连续 |
| TOC 锚点 | 无重复 id，点击能精确跳转 |
| 间距 | 段间距 0、列表项间距 0、块元素间 13.5px |

## 排版颗粒度（写完内容后必查）

飞书导出稿常见「一句一块」「引导句 + 引用块」，直接入库会让页面很碎。
实测一篇 9700 字的文章出现 **889 个视觉块（平均每块 10 字，82% 的 `<p>` 不足 20 字）**。

判断标准（渲染后用真实浏览器数）：

| 指标 | 健康值 | 碎片化 |
| --- | --- | --- |
| 平均每块字数 | ≥ 15 | ≤ 10 |
| `<p>` 中 ≤20 字的占比 | ≤ 40% | ≥ 70% |
| 引用块占视觉块比例 | ≤ 10% | ≥ 20% |

修法：跑 `flatten_quotes.py`（合并短正文 + 引导句与单句引用合为一段）。
注意它**保留「标签型」引用块**（`回答：`/`评估：`/`错误：`/`正确：`）——
这类成组出现，引用块承担视觉分组作用，合了反而丢失清单感。
