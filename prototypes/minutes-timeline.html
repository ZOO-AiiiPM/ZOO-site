1产品方法论 · 需求与推导

结论不重要，推导过程才重要
「关键不是你的结论，关键是你的推导过程」「观念不是是什么，而是为什么」。同样的结论，5 分钟拍脑袋想出来和花两个月调研做出来，表述可能完全一样，但前者是空的。考的就是这个。
需求必须落到数据支撑
价值主张、需求描述都要标注调研数据里的用户占比——「备考没人带，疑问没人解」要写成「调研发现 X% 备考没人带」。否则无法判断这是真需求还是你自己的臆想。
真需求 vs 伪需求的判据
判断真伪需求要有数据支撑，这是产品方法论问题，面试和简历中都要体现这种能力。
to C 项目的需求来源只有两条
有历史用户数据 → 从数据里分析；没有 → 靠市场调研 / 竞品分析。本案选了市场调研（分析小红书帖子得出各需求占比），思路合理且有依据。
调研数据与结论必须对得上
小红书调研显示「代练刷题」排第一，但结论写成「短周期私教、精准提分、查漏补缺」，两者不完整对应。调研与结论不匹配 = 结论失去依据。

2产品方法论 · 背景与现状论述

「系统现状」要写成严谨的三段推导
只说「现状是硬编码约束求解」是客观描述，缺中间论述。完整逻辑应是：现状这么做 → 有什么弊端 → 哪部分需求满足不了 → Agent 有什么优势 → 所以用 Agent。
现状描述要扣回前面分析的需求
背景第一部分分析了需求，第二部分讲现状，就要点出哪些需求在现有方案下无法被支撑，这才形成闭环。
背景的层层递进结构
① 市场情况 → ② 系统 / 能力现状（含弊端）→ ③ 由前两点总结出目标。第三部分是归纳，思路没问题。

3产品方法论 · 目标设定

定性目标必须落地为可量化指标
「把学习服务做到顶尖」这类目标不可衡量——做没做到都说不清。要落地成一整套评价体系：哪些指标必须达成算目标达成，哪些指标不能下降需持续观测。
警惕「所有人群 / 所有场景」
出现「所有人群」通常说明没有目标人群，产品定位模糊，且无法衡量。
推荐以「留存」作为核心验证指标
留存比活跃更合理：活跃受功能频次约束（如期末考试辅导一学期才活跃一次）；留存反映「用户认可后会持续使用」。
目标不清产品就会跑偏
产品不是一个人做——大产品下面有一堆小产品、还有研发，每个人对「顶尖」「所有人群」的理解都不一样，没有指标体系就无法衡量效果。

4产品方法论 · 实现路径与架构

「定位演变」其实是实现路径（路线图）
原文档的「定位演变」不是定位（定位是明确的），而是支撑目标达成的落地实现路径。目标是行业标杆/留存，不可能一步到位，所以要纵向拆阶段。
拆阶段的真正依据是需求，不是技术
「产品第一位的考虑一定不是技术，一定是需求」「千万不要说是因为技术层面」。技术再成熟，需求不存在就没有意义。
MVP 验证的是商业逻辑，不是技术
MVP = 最小成本验证最核心的东西。第一个功能必须是用户需要、且能完整用起来的闭环功能——技术成熟但用户不用，什么都验证不了。
每阶段要有独立价值与量化目标
纵向拆解：每阶段明确闭环掉哪类用户需求（如答疑占比多少）+ 达成什么指标（如用户活跃到多少）。
阶段划分的约束条件
既要考虑用户需求，也要考虑技术实现路径，还要考虑每阶段能否完整闭环、用户能直接用；且单阶段周期建议 1–2 个月——搞半年投入巨大、风险太高。
前后依赖要前置且能独立闭环
若 A 是 B 的前置依赖，且 A 本身能独立满足某需求，通常把 A 放在前面。
阶段排序无标准答案，但论述逻辑必须科学
「1234 还是 1324 没有正确答案」，但排布过程的论述逻辑要科学合理、能自圆其说，且体现出你是依据需求做决策。
用户画像是拆解目标的分析手段
它服务于「为什么这么设计实现路径和功能结构」。画像不能只罗列人群名，要写出各人群占比、特征差异、需求差异（在校 / 在职 / 二战各占多少，各自在乎什么）。
画像结论必须能指导产品设计
分析最终要落到「所以先做答疑」这种可执行的结论上。若不做分人群，也可基于小红书需求做全人群分析——那也是一种分析方法。
需求分层是「体系化思考」的体现
基础 / 进阶 / 高阶要有明确定义与依据（由前期人群分析或市场调研推导），说明各层定位与作用。价值在于——不再把需求看成散点，而是成体系、有规划有方向的东西，是面试和简历中的亮点。
产品架构应是清晰的三层
① 用户可见功能层（答疑、计划、练习、评估、传统资源）② 中间 Agent 引擎层（连接用户与资源、组合拼装）③ 底层学习资源层（题库、知识点）。
先搭 Agent 引擎，再用单功能验证
高顿的学习资源本已现成、公共，你只需整合而非自建。核心是先做 Agent 引擎，用一个功能验证逻辑跑通，再在架构上扩展其他功能。
「功能流程」不等于「产品架构」
学习计划 → 今日任务 → Unit → Graph 更像产品流程/逻辑，只能算一层，不能指导产品构建。
目标拆解与角色无关，落到功能才是产品手段
从目标往前的部分不区分产品/运营角色（运营手段也能实现同一目标）；只有落到产品架构和功能，才叫产品手段。
具体功能模块决策差异小
一旦确定做哪几个模块，后续「答疑模块怎么做」各家差别不大——真正体现区别的是前面的分析。

5AI 产品经理核心能力 · 评测

AI 产品的核心不是功能设计，而是功能评价（评测）
系统级 PRD 只讲系统交互、功能组合，没碰到 AI 产品的核心，应聘 AI PM 有难度。「AI 产品的第一件事……是评测」。
评测第一层：正确率（对错标注）
AI 不是 100% 正确，一定存在准确率。怎么衡量准确率是首先要考虑的：输入 query → 看答案对不对 → 直接标对错。
评测第二层：好坏（解析质量）
只判对错不够。像买练习册会看解析详不详细、看不看得懂——解析可能才是关键。需把「好」标准化到可标注，例如追问「什么叫详细」：关键推理步骤不能跳步，哪些步可跳、哪些不可跳。
评测第三层：个性化适配
好学生觉得解析太详细啰嗦，差学生嫌不够详细。理想态是按学生历史学习情况区分模式——但一旦引入个性化，评测会变得更复杂（不同模式要分别评标准）。
评测方式的选择依据是产品目标
定位是「个性化答疑」→ 要做到第三层；第一期只做「给出正确答案、让用户快速找到答案」→ 第一层就够。没有目标，就不知道做到哪一层。

6AI 产品经理核心能力 · 错误处理

必须设计「错误感知机制」
前提是你得能感知到它错了：AI 答不出来用户能感知；或 RAG 检索时按答案置信度低于阈值就不输出、转人工介入。
区分「未召回」与「召回但出错」两种情况
召回（recall）失败该怎么补救？召回成功但答案错了又该怎么感知和处理？这是 AI 产品经理要设计的策略。
兜底方案决定准确率门槛
现有策略是真人老师兜底。若有感知能力 + 兜底方案，准确率门槛可低一些；若完全无法感知错误，则准确率必须做到 98–99% 才能上线。
可按场景拆分准确率要求
要区分「什么样的问题允许准确率低一点」「什么问题是坚决不能错的」。
准确率要求决定实现方案
要求 90–93% → 写个 skill / 用提示词 + 简单向量检索即可，成本最低；要求 99% → 不能让模型自己检索（一定会出错），要用结构化题库 + 工具直接查题确保零错。
AI 产品的技术选型清单
写 skill、做工具、RAG 检索、纯向量检索、query 改写（可做可不做）、总结（可做可不做）——这些都要 AI 产品经理决策，依据就是准确率要求。

7AI 产品经理核心能力 · 测评流程与结果

上线前的离线测评
冷启动没有足够数据时，要解决「人怎么造数据、怎么让它尽可能接近真实」。
AI 产品必须灰度
灰度对 AI 产品尤其重要（普通功能产品还好）：先积累数据，验证线上准确率，再评价线上效果。
线上持续监控
上线后还有后续持续的效果监控，评测标准沿用之前定的那套。
离线与线上指标可能不同（进阶）
举例：质检项目离线测精准率+未召回的召 correctness，但线上数据量大、资源有限，只检召回部分的准确率，未召回的假定正确——两者标准就有差异。本场景一般用同一套即可。
结果要覆盖三层
① 既定目标是否完成 ② 过程指标：准确率的初始值 → 提升路径 → 最终值（这是关键贡献）③ 业务收益：留存等最终目标达成多少。
准确率 → 留存的链路如何论证
难完全量化时用拆解逻辑说清：用户要的是「100% 不出错」，出错就不会再用 → 所以准确率必须达标 → 准确率只有 60% 连上线都上不了。留存 = 功能找对了 + 满足了用户需要。

8简历撰写规范

先写工作职责概述（与项目无关）
工作经历下面第一段写：你承担的岗位是什么、职责是什么、OKR 是什么。
紧接着写任内成果（2–3 行）
只写概述还不够，要在第一段末尾说明你任内达成了什么成果，控制在两到三行以内。
项目按五段式写
① 背景 ② 目标 ③ 方案/方法（怎样达成目标的落地手段）④ 关键点/难点/个人贡献 ⑤ 成果。
段落可按需合并
背景和目标可以合并成一段；方法和关键点也可以合并，看篇幅多少。
关键点是体现能力的地方
写实现目标最核心的几个要素，例如：Agent 的 skill 设计、「答疑正确率要求 100% 不能错」这个关键点、你分析了哪几条实现路径、最终为何选定这条。写 2–3 个点，没有写 1 个也 OK。
成果要扣回目标达成情况
既有关键过程指标（对 AI 而言就是准确率达成多少），也有最终业务效果（上线后留存等）。
项目论述必须与简历一致
简历写项目时同样按这五部分，不区分是面试讲还是写简历。
